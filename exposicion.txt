1. IDEA GENERAL DEL TRABAJO

Este proyecto analiza una base de usuarios de una plataforma de streaming. La intencion no fue solamente aplicar codigo o generar graficos, sino construir un proceso completo de mineria de datos: inspeccionar, detectar problemas, limpiar con criterio, analizar, aplicar PCA y comunicar resultados.

La guia del trabajo final pide que las decisiones esten justificadas con evidencia. Por eso, cada etapa del proyecto busca responder una pregunta concreta:

- Que contiene la base?
- Que problemas de calidad tiene?
- Como se corrigen esos problemas sin modificar el archivo original?
- Que patrones aparecen en los usuarios?
- Que aporta PCA despues de escalar las variables?
- Que conclusiones se pueden defender y que limitaciones existen?

La idea central para defender el trabajo es esta: antes de interpretar datos, hay que prepararlos bien. Si la base tiene duplicados, categorias mal escritas, fechas invalidas o valores extremos, cualquier conclusion puede sonar convincente pero estar apoyada en ruido.

3. DATASET

El dataset original se llama streaming_users_dirty.json. Cada fila representa un usuario de una plataforma de streaming.

Columnas principales:

- user_id: identificador del usuario.
- age: edad.
- subscription_plan: plan de suscripcion.
- monthly_watch_time_mins: minutos de visualizacion mensual.
- country: pais.
- favorite_genre: genero favorito.
- last_login_date: fecha del ultimo login.
- customer_support_tickets: cantidad de tickets de soporte.

La base original tenia 8160 filas y 8 columnas. El dataset procesado final queda con 8000 filas y las mismas 8 columnas. Esto es importante porque se respeto la indicacion de no crear columnas nuevas en el dataset final.


4. INSPECCION INICIAL

La inspeccion inicial se desarrollo en 01_inspeccion_inicial.ipynb.

En esta etapa no se limpiaron datos. La intencion fue mirar la base y reunir evidencia.

Se reviso:

- cantidad de filas y columnas;
- tipos de datos;
- valores faltantes;
- duplicados exactos;
- user_id repetidos;
- valores unicos en variables categoricas;
- estadisticas descriptivas de variables numericas;
- posibles outliers o valores imposibles.

Problemas encontrados:

- habia duplicados exactos;
- habia user_id repetidos;
- habia categorias escritas de distintas formas;
- habia nulos en monthly_watch_time_mins, favorite_genre y last_login_date;
- habia edades imposibles, como valores negativos, cero o edades demasiado altas;
- habia tiempos de visualizacion negativos o extremos;
- habia tickets de soporte negativos o extremos;
- habia fechas invalidas o futuras.

Esta etapa se conecta con la limpieza porque no se aplicaron transformaciones automaticas. Primero se observo la evidencia y despues se decidio que hacer.


5. LIMPIEZA Y PREPARACION

La limpieza se desarrollo en 02_calidad_y_limpieza.ipynb.

La regla principal fue preservar el dataset original y trabajar sobre una copia. Esto es una practica profesional porque permite auditar el proceso y volver al punto inicial si hace falta.

5.1 Duplicados exactos

Primero se eliminaron filas completamente iguales. Si dos filas son identicas en todas las columnas, mantener ambas duplica informacion y puede sesgar conteos o promedios.

5.2 User_id repetidos

Despues se revisaron usuarios repetidos por user_id. Esta parte es importante para defender.

No se eligio una fila al azar. Para decidir que registro conservar se priorizo:

1. que last_login_date fuera una fecha real;
2. que monthly_watch_time_mins fuera un consumo plausible;
3. que el consumo mensual estuviera cerca del consumo tipico de la base;
4. que la fecha fuera mas reciente;
5. que el registro estuviera mas completo.

Por que se hizo asi?

Porque user_id identifica a una persona. Si un mismo usuario aparece mas de una vez, conviene conservar el registro de mejor calidad. monthly_watch_time_mins y last_login_date son claves porque ayudan a diferenciar un dato real de un posible error de carga.

Ejemplo de razonamiento:

Si un usuario aparece con un consumo de -1 o 99999 minutos, ese dato no representa bien el comportamiento real. Si otra fila del mismo usuario tiene una fecha valida y un consumo razonable, esa fila es mas confiable.

5.3 Estandarizacion de categorias

Se normalizaron plan, pais y genero favorito.

Ejemplos:

- Premium, premium y Premium con espacios deben ser una sola categoria.
- Brasil, Brazil y BRA deben representar Brasil.
- Crime, Crimen y CRIME se estandarizan como Crimen.

Por que es importante?

Porque si no se estandarizan, el analisis cuenta categorias falsas. Por ejemplo, el mismo plan podria aparecer dividido en varias etiquetas y distorsionar los graficos.

5.4 Valores imposibles

Se trataron como nulos los valores que no eran creibles:

- age menor a 13 o mayor a 100;
- monthly_watch_time_mins negativo;
- customer_support_tickets negativo;
- fechas invalidas o futuras.

No se eliminaron automaticamente las filas porque eso podria perder informacion util. En cambio, se convirtieron esos valores a nulos y luego se imputaron con criterio.

5.5 Fechas

La columna last_login_date tenia varios problemas:

- fechas faltantes;
- formatos distintos;
- fechas invalidas;
- fechas futuras.

Primero se intento parsear las fechas en formato principal. Luego se intento leer otros formatos posibles. Las fechas que no se pudieron interpretar pasaron a nulo. Tambien se pasaron a nulo las fechas posteriores a la fecha de referencia del trabajo.

Despues se imputaron con la fecha mediana. Se uso mediana porque representa una fecha central y es mas robusta que una media frente a fechas extremas.

5.6 Imputacion

La imputacion se hizo despues de convertir errores a nulos.

Para variables numericas se usaron medianas segmentadas por subscription_plan y country. La mediana es robusta frente a outliers.

Para variables categoricas se usaron modas segmentadas. Es decir, se completo con el valor mas frecuente dentro de grupos comparables.

5.7 Winsorizacion

La winsorizacion se aplico a:

- monthly_watch_time_mins;
- customer_support_tickets.

Winsorizar no es eliminar. Significa limitar valores extremos a un maximo razonable.

Por que se aplico?

Porque algunos valores extremos podian romper la escala de graficos, promedios, correlaciones y PCA. Si casi todos los usuarios tienen entre 0 y 4 tickets, valores como 99 o 150 pueden dominar la lectura completa.

La idea fue conservar el registro del usuario, pero evitar que un valor probablemente no representativo maneje todo el analisis.

No se hizo winsorizacion en age. En edad, los valores imposibles se trataron como errores y se imputaron, porque una edad negativa o 150 no es un extremo valido: es un problema de calidad.

7. ANALISIS EXPLORATORIO EDA

El EDA se trabajo en 03_eda.ipynb y en Streamlit.

La guia pide:

- 2 visualizaciones univariadas;
- 2 visualizaciones bivariadas;
- 1 visualizacion multivariada;
- interpretacion para cada resultado.

7.1 Univariado 1: monthly_watch_time_mins

Se analizo la distribucion del tiempo mensual de visualizacion.

Objetivo:
entender el comportamiento general del consumo.

Interpretacion:
La mayoria de usuarios se concentra en consumos medios y existe una cola de usuarios intensivos. Esto muestra que no alcanza con mirar el promedio, porque los usuarios intensivos pueden empujarlo hacia arriba.

7.2 Univariado 2: subscription_plan

Se analizo la cantidad de usuarios por plan.

Objetivo:
entender la composicion de la base.

Interpretacion:
Saber cuantos usuarios hay por plan ayuda a contextualizar comparaciones. Si un plan tiene muchos mas usuarios que otro, los resultados agregados pueden estar influenciados por ese segmento.

7.3 Bivariado 1: age vs monthly_watch_time_mins

Se cruzo edad con consumo mensual.

Objetivo:
ver si la edad explica el consumo.

Interpretacion:
La edad aporta contexto, pero no explica sola el comportamiento de visualizacion. Si los puntos aparecen dispersos, significa que usuarios de distintas edades pueden tener consumos parecidos y usuarios de la misma edad pueden consumir muy distinto.

7.4 Bivariado 2: monthly_watch_time_mins por subscription_plan

Se comparo consumo mensual segun plan.

Objetivo:
ver si el consumo cambia entre planes.

Interpretacion:
El boxplot permite comparar medianas y dispersion. Si un plan muestra una mediana mas alta, puede sugerir usuarios mas intensivos en ese segmento.

7.5 Multivariado: age, monthly_watch_time_mins y favorite_genre

Se cruzaron edad, consumo mensual y genero favorito.

Objetivo:
ver si los patrones de consumo por edad cambian segun preferencia de contenido.

Interpretacion:
El genero favorito agrega contexto. Si un genero concentra consumos mas altos, puede sugerir contenidos que generan mayor permanencia o usuarios mas intensivos.

La idea general del EDA es pasar de una lectura simple a una lectura mas rica:

primero una variable,
despues dos variables,
finalmente tres variables.


8. PCA Y ESCALAMIENTO

PCA se trabajo en 04_pca.ipynb y en Streamlit.

Variables usadas:

- age;
- monthly_watch_time_mins;
- customer_support_tickets.

Antes de PCA se aplico StandardScaler, es decir, estandarizacion Z-score.

Por que se escalo?

Porque las variables tienen unidades distintas:

- edad esta en anios;
- consumo esta en minutos;
- soporte esta en cantidad de tickets.

Si no se escala, monthly_watch_time_mins podria dominar PCA solo porque sus numeros son mas grandes. Escalar permite que cada variable participe segun su variabilidad relativa, no segun su unidad de medida.

Que hace PCA?

PCA resume variables numericas en componentes principales. Estas componentes son combinaciones de las variables originales y buscan capturar la mayor cantidad posible de variabilidad.

Como se interpreta?

- La varianza explicada indica cuanta informacion resume cada componente.
- La proyeccion PC1-PC2 permite observar si hay agrupamientos o separaciones por plan.
- Si los grupos se mezclan, tambien es una conclusion valida: significa que esas variables numericas no separan fuertemente los planes.

Importante para defensa:

PCA no es un modelo predictivo.
PCA no prueba causalidad.
PCA es una herramienta exploratoria para resumir y visualizar estructura numerica.

11. CONCLUSIONES PRINCIPALES

Conclusion metodologica:

La limpieza es una parte central del analisis. Sin preparar los datos, se corre el riesgo de interpretar errores como si fueran patrones reales.

Conclusion sobre usuarios:

El consumo mensual es una variable clave para entender perfiles. Sin embargo, edad, plan y genero favorito agregan contexto. No todos los usuarios se comportan igual.

Conclusion sobre PCA:

PCA ayuda a resumir las variables numericas y ver perfiles generales, pero no reemplaza el EDA ni permite afirmar causas.

Conclusion sobre limites:

El dataset no incluye variables como churn, precio, fecha de alta, satisfaccion, dispositivo o historial completo de sesiones. Por eso las conclusiones son descriptivas.


12. LIMITACIONES

Las principales limitaciones son:

- no hay variable de abandono o churn;
- no hay precio pagado;
- no hay antiguedad del usuario;
- no hay satisfaccion;
- no hay detalle de sesiones;
- no hay informacion de dispositivo;
- las fechas de login permiten una lectura parcial de actividad, pero no retencion completa.

Esto significa que se pueden describir patrones, pero no afirmar causalidad ni predecir abandono.

14. POSIBLES PREGUNTAS DE DEFENSA Y RESPUESTAS

Pregunta: Por que no modificaste el dataset original?

Respuesta: Porque una buena practica es preservar la fuente original. El archivo original queda en data/raw/ y todas las transformaciones se aplican sobre una copia. Esto permite auditar el proceso.

Pregunta: Como resolviste user_id repetidos?

Respuesta: Primero elimine duplicados exactos. Para user_id repetidos no exactos, conserve la fila de mayor calidad, priorizando fecha real, consumo mensual plausible, cercania al consumo tipico y completitud.

Pregunta: Por que convertiste valores imposibles a nulos?

Respuesta: Porque una edad negativa, un consumo negativo o una fecha invalida no representan informacion real. Convertirlos a nulos permite tratarlos de forma explicita en la imputacion.

Pregunta: Por que usaste mediana?

Respuesta: Porque la mediana es robusta frente a valores extremos. En una base con outliers, la media puede quedar distorsionada.

Pregunta: Que es winsorizacion?

Respuesta: Es limitar valores extremos a un maximo razonable. No elimina usuarios, solo evita que valores exagerados dominen el analisis.

Pregunta: Por que winsorizaste consumo y tickets?

Respuesta: Porque habia valores extremos que podian distorsionar graficos, correlaciones y PCA. En cambio, en edad trate los valores imposibles como errores, no como extremos validos.

Pregunta: Por que escalaste antes de PCA?

Respuesta: Porque PCA es sensible a la escala. Si no se escala, la variable con numeros mas grandes, como minutos de consumo, puede dominar el resultado.

Pregunta: PCA predice algo?

Respuesta: No. PCA no es un modelo predictivo. Es una tecnica exploratoria para reducir dimensionalidad y resumir variabilidad.

Pregunta: Que significa que una correlacion sea baja?

Respuesta: Significa que no hay una relacion lineal fuerte entre esas variables. Pero puede haber patrones por segmentos que la correlacion general no capture.

Pregunta: Cual es la principal conclusion del trabajo?

Respuesta: Que la preparacion de datos fue necesaria para llegar a una base confiable y que el comportamiento de usuarios de streaming se entiende mejor combinando consumo, edad, plan y genero favorito, no mirando una sola variable.
